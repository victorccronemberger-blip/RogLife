# MainWindow source boundaries

`MainWindow.cpp` is the facade and page router. `MainWindowComponents.cpp` builds the shared shell and reusable cards, metrics and buttons. `MainWindowService.cpp` owns the backend process, update flow, readiness transition and window shutdown. `MainWindowDashboard.cpp` owns Home, Readiness, storage selection and diagnostics; `MainWindowMonitoring.cpp` owns the banned account monitor. Feature page construction and behavior live together in `MainWindowIntegrations.cpp`, `MainWindowCampaigns.cpp`, `MainWindowAccounts.cpp`, `MainWindowBalances.cpp` and `MainWindowLibrary.cpp`. The former all-pages translation unit has been removed. `MainWindowSupport.hpp` contains translation-unit-local shared UI/service helpers, and `DevelopmentProjectRoot.hpp` resolves a development checkout by its `moneymin/web/__main__.py` marker with a configured-root fallback.

Cross-sector behavior uses narrow facade methods. Campaign removals call `notifyPermanentCampaignAccountRemoval`; Accounts and Balances each remove their own cached/table state. Library asks Campaigns for task-selection names and dataset state, and asks it to select the combined catalog. Campaigns delegates its Nymeria tab activation to Library. Readiness reads the campaign dataset through `selectedCampaignDataset`. Backend generation changes and window closing dispatch to per-sector handlers, which own their timers and feature-specific reset/recovery behavior. Navigation similarly sends page activation to the owning sectors.

The cross-sector contracts are explicit, while `MainWindow` still owns the `ApiClient`, backend generation, global ready/closing flags, widget pointers and all feature state in one private class. This keeps the existing `LocalEditionTests` friend access and avoids changing QObject lifetime or callback ownership. Separating the state into controller objects would require migrating those test seams and defining ownership for the shared API client and operation generation.

CMake uses one source list for both `QMoney` and `local_edition_tests`, including every feature module. The Qt root-selection contract is filesystem-only; the Qt suite is run offscreen and does not start the user service.

Campaign catalog monitoring lives in `MainWindowCampaigns.cpp`: its timer, status label and progress bar report actual category/provider counters, elapsed time and the last service response. Unknown totals use an indeterminate bar; a stage percentage is not an estimate of remaining time. `ApiClient` cancels only obsolete task-catalog polling chains when the selection changes; this does not repeat productive writes or cancel a backend worker. A pending worker remains recoverable through the existing job identity.

Provider indexing belongs to `MainWindowCatalogs.cpp`, including its independent selectors, progress percentage, summary and backend lifecycle handler. Its navigation entry is appended at index 9, preserving existing page indices. It submits preparation once and polls the returned job with GET; it does not select accounts or start uploads. Native campaigns request prepared indexes and direct the user here when those indexes are absent or invalid. Integrations retains credential/source setup and its explicit Ego4D source-install button; merely opening the application does not initiate that installation.
