# MainWindow source boundaries

Mobile maintenance is mapped in `../../docs/modularizacao/CELULAR.md`. `MainWindowMobile.cpp` owns the existing `renderAppCheckSnapshot` and `recheckAppCheck` implementations. Integrations still constructs its card and requests the aggregate snapshot; the shared declarations, widget pointers, callback generation and lifecycle remain unchanged. `AndroidDevicePanel` and `UsbDeviceWatcher` keep their separate ownership. General integration or campaign work must consume these interfaces without changing mobile authentication internals unless explicitly requested.

`MainWindow.cpp` is the facade and page router. `MainWindowComponents.cpp` builds the shared shell and reusable cards, metrics and buttons. `MainWindowService.cpp` owns the backend process, update flow, readiness transition and window shutdown. `MainWindowDashboard.cpp` owns Home, Readiness, storage selection and diagnostics; `MainWindowMonitoring.cpp` owns the banned account monitor. Feature page construction and behavior live together in `MainWindowIntegrations.cpp`, `MainWindowCampaigns.cpp`, `MainWindowAccounts.cpp`, `MainWindowBalances.cpp` and `MainWindowLibrary.cpp`. The former all-pages translation unit has been removed. `MainWindowSupport.hpp` contains translation-unit-local shared UI/service helpers, and `DevelopmentProjectRoot.hpp` resolves a development checkout by its `moneymin/web/__main__.py` marker with a configured-root fallback.

Cross-sector behavior uses narrow facade methods. Campaign removals call `notifyPermanentCampaignAccountRemoval`; Accounts and Balances each remove their own cached/table state. Library asks Campaigns for task-selection names and dataset state, and asks it to select the combined catalog. After a Nymeria library update, Library calls `refreshCampaignTasksAfterNymeriaUpdate`; Campaigns owns invalidation and reloading of its catalogue. Campaigns delegates its Nymeria tab activation to Library. Readiness reads the campaign dataset through `selectedCampaignDataset`. Backend generation changes and window closing dispatch to per-sector handlers, which own their timers and feature-specific reset/recovery behavior. Navigation similarly sends page activation to the owning sectors.

The cross-sector contracts are explicit, while `MainWindow` still owns the `ApiClient`, backend generation, global ready/closing flags, widget pointers and all feature state in one private class. This keeps the existing `LocalEditionTests` friend access and avoids changing QObject lifetime or callback ownership. Separating the state into controller objects would require migrating those test seams and defining ownership for the shared API client and operation generation.

CMake uses one source list for both `QMoney` and `local_edition_tests`, including every feature module. The Qt root-selection contract is filesystem-only; the Qt suite is run offscreen and does not start the user service.

Campaign catalog monitoring lives in `MainWindowCampaigns.cpp`: its timer, status label and progress bar report actual category/provider counters, elapsed time and the last service response. Unknown totals use an indeterminate bar; a stage percentage is not an estimate of remaining time. `ApiClient` cancels only obsolete task-catalog polling chains when the selection changes; this does not repeat productive writes or cancel a backend worker. A pending worker remains recoverable through the existing job identity.

Provider indexing belongs to `MainWindowCatalogs.cpp`, including its independent selectors, progress percentage, summary and backend lifecycle handler. Its navigation entry is appended at index 9, preserving existing page indices. It submits preparation once and polls the returned job with GET; it does not select accounts or start uploads. Native campaigns request prepared indexes and direct the user here when those indexes are absent or invalid. Integrations retains credential/source setup and its explicit Ego4D source-install button; merely opening the application does not initiate that installation.

The campaign preparation shortcut calls `openProviderCatalogsForCampaign` with its provider and duration range. Catalogs owns applying those values and preserves an active preparation's selection. A finished preparation that materializes an index calls `refreshCampaignTasksAfterProviderPreparation`; Campaigns owns invalidating obsolete category reads and preserving its selections for the next refresh. An Ego4D prepared read can filter an existing valid base index for another duration range without classification or persistence. Additional duration-specific cuts still belong to explicit preparation.

`AndroidDevicePanel` is the public USB diagnostic component displayed at the top of Campaigns. It owns a visible-page `UsbDeviceWatcher` subscription to Windows USB arrival/removal notifications and receives service availability through the campaign lifecycle handler. There is no periodic device polling: an initial read, explicit refresh/selection and coalesced USB events request public diagnostics. Its single-shot 200 ms timer only coalesces notification bursts. Pending reads and transient failures preserve the last USB observation with a stale/error indication; confirmed disconnection and unavailable authorization remain explicit. An absent selected device retains its serial rather than switching to an emulator. Its read-only integration endpoint lists authorized/offline devices and reads public Android properties, shell identity and `su` executable availability. It neither elevates privileges nor accesses application data. A USB connection or available `su` is not evidence of application authentication or accepted uploads; campaign execution and receipts remain owned by their existing modules.

Dataset campaign admission, catalogue preview and hourly capacity reads use the prepared-index policy. An absent or changed Ego4D/Nymeria index returns `provider_catalog_preparation_required` and directs the user to Catalogs. This is a local preparation issue, not an account restriction; it must propagate through provider selection without silently approving a partial plan. Accepted review receipts retain their frozen plan and start identity. Cache/both compatibility remains unchanged.

Balances owns its read revision and single pending GET. Late replies are discarded after page changes, backend generation changes or closing; refresh intents coalesce, and polling only runs on the visible, ready balances page. Confirmed totals, filter eligibility and payout state come from the existing wallet contract. Saved historical amounts remain labelled in the table, Claru summary and CSV, with the reason provided by the service; missing wallet confirmation never becomes a current balance.

The shell's three-second live refresh dispatches passive observations to the visible page owner; it does not reload editable forms or issue productive writes. Page revisions discard responses across navigation and backend generations. Each owner prevents overlapping reads, preserves user selections, and records the last observed response in the footer. Readiness uses a fifteen-second cadence and reuses its storage snapshot; the accelerator uses its lightweight `live=1` observation. Hidden/minimized windows and modal editing suspend new passive reads. Existing operation-specific timers continue to own their progress.

Explicit provider preparation obtains source annotations before opening a fresh selection snapshot and persisting indexes. Catalogs owns its one-second progress clock and recovers the existing selection/job with GET after an observation failure. A successful HTTP response alone does not establish readiness; partial source failures remain visible. Video and sensor acquisition still belongs to the existing campaign/library operations. The existing heavy-operation barrier reserves provider preparation in the per-app catalog loader and excludes overlapping campaign starts, recovery, library preparation and accelerator work; observation remains available throughout.
